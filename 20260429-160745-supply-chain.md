## Open issues

### Top tier — self-fetch from a moving ref

- `scripts/get-branch-metadata.sh:19` — `curl -s -f -L https://raw.githubusercontent.com/rancher/dashboard/master/branches-metadata.json` pulls JSON from `master` of our own repo and feeds it into `jq` to drive subsequent fetch URLs in `scripts/build-e2e`. Anyone with push access to `master` (or any cross-branch attack on the raw mirror) controls the bytes. Pin the URL to a 40-hex SHA, vendor the file, or use a relative path / `git show $(git merge-base origin/master HEAD):branches-metadata.json`. (see wiki §3.5)

### Container images (unpinned base)

- `shell/scripts/extension/helm/package/Dockerfile:1` — `FROM registry.suse.com/bci/bci-base:15.5` has no `@sha256:` digest. Add a digest: `FROM registry.suse.com/bci/bci-base:15.5@sha256:<hex>`. The trailing tag lets Renovate update; the digest is what's verified at pull. (see wiki §3.4)

### Inline downloads (curl/wget without checksum)

- `scripts/build-e2e:40` — `curl https://releases.rancher.com/dashboard/latest/index.html -k -o $OUTPUT_DIR/index.html` is fetched into the e2e build artifact and served by the test harness. No checksum, no TLS verification (`-k`), and `latest/` is a moving ref. Either (a) build the dashboard from source unconditionally, (b) drop `-k` and pin to a versioned URL with a stored sha256, or (c) document the artifact as untrusted-by-design and confirm the e2e suite never executes it. (see wiki §3.5)
- `scripts/build-e2e:62` — `curl $EMBER_URL -k -o $OUTPUT_EMBER_DIR/index.html` — same pattern as above; `$EMBER_URL` defaults to `https://releases.rancher.com/ui/latest2/index.html` and is overridden via the JSON pulled by `scripts/get-branch-metadata.sh` (which is itself unpinned, see top tier). Apply the same fix.
- `shell/scripts/extension/publish:400` — `wget -P ${BASE_DIR} https://raw.githubusercontent.com/${GITHUB_SOURCE}/${GITHUB_BRANCH}/index.yaml` pulls a Helm chart index from a branch (default `main`) and merges it into the locally-rebuilt index. The merged index is then published to `gh-pages`. A tampered `index.yaml` could redirect chart consumers to an attacker URL. Pin to a SHA or run `helm repo index --merge` against the bytes after a digest check. (see wiki §3.5)

### Run-from-network

- `scripts/e2e-k3s-start:81` — `kubectl apply -f https://github.com/jetstack/cert-manager/releases/download/v1.7.1/cert-manager.crds.yaml` is version-pinned but not digest-verified. The script verifies `K3S_CHECKSUM` and `HELM_CHECKSUM` for the two adjacent downloads (lines 53–58, 69–75) — adopt the same pattern: `curl -sfL -o crds.yaml https://github.com/.../v1.7.1/cert-manager.crds.yaml && echo "<sha256> crds.yaml" | sha256sum -c && kubectl apply -f crds.yaml`. (see wiki §3.5)
- `cypress/scripts/build.sh:60` — `npx tsc --project tsconfig.build.json` runs without a pinned version. In practice `tsc` resolves to the local `node_modules/.bin/tsc` (yarn-installed, integrity-checked) so the registry fallback is unlikely; advisory only. Replace with `yarn run tsc` or `node_modules/.bin/tsc` to remove the registry path entirely. (see wiki §3.6)

### `git clone` in build/install scripts (cloned code is later executed)

- `cypress/jenkins/init.sh:36` — `git clone -b "${QA_INFRA_BRANCH}" "${QA_INFRA_REPO}" "${QA_INFRA_DIR}"` defaults to `https://github.com/rancher/qa-infra-automation.git` at branch `main`. The clone is then used to (a) `docker build` a runner image from `Dockerfile.quickstart` (line 44) and (b) execute the ansible playbook inside it (line 222). Cloned bytes are executed. Pin `QA_INFRA_BRANCH` to a 40-hex SHA in the Jenkins job config and add a post-clone `git checkout <sha>` guard. (see wiki §3.5)
- `shell/scripts/test-plugins-build.sh:201` — `git clone https://github.com/$REPO_ORG/$REPO_NAME.git` clones five upstream extension repos (kubewarden, neuvector, harvester, ali, virtual-clusters), runs `yarn install --frozen-lockfile` + `yarn build-pkg` against each, and the build executes their build scripts. A compromise of any of those repos' default branches lands arbitrary code in our CI. Pin each clone to a SHA via `--branch <sha>` (use a small JSON manifest at the top of the script so Renovate can update it). (see wiki §3.5)

### GitHub Actions token permissions — missing top-level block (default = read/write)

- 26 workflows lack a top-level `permissions:` declaration, so each job runs with the repo-default token (commonly `read/write` on legacy repos). With `actions/`, `id-token`, and `packages` write available by default, a compromised pinned action can publish artifacts, mint OIDC tokens, or push code. Add `permissions: read-all` at the workflow level and grant the narrowest `write` per-job that needs it.
- Workflows: `add-issue-labels.yaml`, `automation-candidate.yaml`, `build-and-upload-branch.yaml`, `build-and-upload-release.yaml`, `build-and-upload.yaml`, `build-extension-catalog.yml`, `build-extension-charts.yml`, `build-extensions-test.yml`, `build-test.yaml`, `check-plugins.yaml`, `code-coverage.yaml`, `create-pr-build-extension-charts.yml`, `docusaurus.yaml`, `extensions-compatibility-tests.yaml`, `port-issue.yaml`, `port-pr.yaml`, `pr-gh-project-processor.yaml`, `pr-gh-project.yaml`, `rancher-components.yaml`, `storybook.yaml`, `test-extension-workflows-master.yml`, `test-extension-workflows-release-2.8.yml`, `test-extension-workflows-release-2.9.yml`, `test.yaml`, `update-cloud-data.yml`, `valid-pr.yaml`.

### GitHub Actions token permissions — sensitive-write scopes

The 52 sensitive-write findings split into two categories:

**Privileged automation that legitimately needs the scope.** The seven `*.lock.yml` files (`agentics-maintenance.yml`, `daily-test-improver.lock.yml`, `pr-fix.lock.yml`, etc.) are autogenerated by gh-aw and need `contents: write` to push branches/commits, `actions: write` to manage agentic state, and `id-token: write` for OIDC artifact attestation. The lock-file headers pre-pin every action and image by SHA, so the privileged token only ever runs vetted code. No action.

**Hand-written workflows where the scope can likely be narrowed.** Surface these for review:

- `.github/workflows/auto-retry.yaml:17` (workflow) — `actions: write`. Only re-runs failed jobs; verify `actions: write` is the minimum (the `gh run rerun` API path).
- `.github/workflows/automation-candidate.yaml:17` (job) — `id-token: write` for an issue-labelling workflow looks unnecessary; remove unless an OIDC consumer is downstream.
- `.github/workflows/build-extension-catalog.yml:37,39` (job) — `actions: write` + `packages: write`; the latter is needed to publish the catalog image, the former should be reviewed.
- `.github/workflows/build-extension-charts.yml:42,120-123` and `.github/workflows/test-extension-workflows-*.yml` — `actions/contents/deployments/pages: write` cluster; the gh-pages publish needs `contents/pages` but the `actions/deployments` writes look incidental.
- `.github/workflows/create-pr-build-extension-charts.yml:30,96` — `actions: write`, `contents: write`. The PR-creating workflow needs `contents` (commit) and `pull-requests: write` (already present), but `actions: write` is unusual.
- `.github/workflows/docusaurus.yaml:49,50` — `pages: write`, `id-token: write`. Standard GitHub Pages deploy pair; keep.
- `.github/workflows/fossa.yaml:14` (workflow) — `id-token: write` so FOSSA can attest builds; keep if attestation is consumed.
- `.github/workflows/port-issue.yaml:15` and `port-pr.yaml:12-14` — `id-token: write`, `contents: write`, `actions: write`; backport bots need `contents`/`pull-requests`, but `id-token`/`actions` look incidental.
- `.github/workflows/release-{cypress-pkg,rancher-components,shell-pkg}.yaml` — `id-token: write` for npm provenance; keep.
- `.github/workflows/update-cloud-data.yml:13,14,16` — `actions: write`, `contents: write`, `id-token: write`. The `id-token: write` is unusual for a pure data-update workflow; remove unless explicitly attesting.

## Retro: dependency types not explicitly covered

### R1 — `kubectl apply -f <pinned-version-URL>` falsely classified as verified

**Where**: `scripts/e2e-k3s-start:81`.

**Why missed**: `inventory.py`'s `run_from_network[]` detector recognises `kubectl apply -f URL` and runs the ±30-line verifier scan. The window picked up `K3S_CHECKSUM` / `HELM_CHECKSUM` blocks for the two unrelated downloads on lines 53–58 and 69–75 and stamped this entry `verifier ✓`. The verifier targets `k3s-script` and `get_helm.sh`, not `cert-manager.crds.yaml`.

**Proposed change**: For `run_from_network[]` `kubectl apply -f URL` entries, require the verifier line to name the URL's filename basename (`cert-manager.crds.yaml`) or to live in the `±10` line window. The same destination-name match already exists for `curl`/`wget` candidates per the Phase 2 rules — extend it to `kubectl apply -f` and to `helm install` from a remote chart.

### R2 — `gh-aw` agentic-workflow lock.yml manifests as a first-class pinning signal

**Where**: `.github/workflows/*.lock.yml` (7 files, e.g. `daily-accessibility-review.lock.yml`).

**Why missed**: The script's existing GHA + container-image scanners parse the compiled body and report what they find, which means each lock.yml looks like an unpinned-permissions soup of sensitive-writes. But the file's `gh-aw-manifest` header (line 2) embeds a structured manifest that pre-pins every `actions[].sha` and `containers[].digest` and lists every secret the workflow can touch. Treating the manifest as authoritative would:

- Confirm the body's pinning posture without re-parsing every `uses:` and `image:` line in a 1500-line generated file.
- Distinguish "compiled from .md spec, audit the manifest" from "hand-written workflow, audit each line."

**Proposed change**: Add a `gh_aw_lock_files[]` section to the inventory. For each `.lock.yml` whose first comment line matches `# gh-aw-metadata:`, parse the second comment line (`# gh-aw-manifest:`) as JSON and emit `compiler_version`, `actions[]`, `containers[]`, `secrets[]`. In Phase 2 and Phase 3, suppress the per-line `uses:` / `image:` and `permissions:` findings for these files when `actions[].sha` matches every `uses:` SHA in the body — surface a single `Pinned dependencies › gh-aw lock files` row instead. Hand-written privileged scopes still warrant per-finding bullets so they're visible in the report.

### R3 — `git clone` followed by `docker build` / `yarn build-pkg` should rate higher than `git clone` followed by `diff`

**Where**: `cypress/jenkins/init.sh:36-46`, `shell/scripts/test-plugins-build.sh:201-220`, `.github/workflows/scripts/check-creators-workflows-code.sh:89` (compare).

**Why missed**: The script's `git_clones_in_scripts[]` flags every non-SHA clone uniformly. There's no notion of "what does the script do with the clone." A clone that feeds `docker build` or `yarn build-pkg` is in the same threat tier as `curl | bash`; a clone that feeds `diff` is advisory.

**Proposed change**: After detecting a `git clone`, scan the next ~50 lines (or the rest of the function body) for `docker build`, `yarn build`, `yarn install`, `npm install`, `make`, `cargo build`, `go build`, `ansible-playbook`, `python setup.py install`, `pip install -e .`. When any match: tag the entry `executes_cloned_code: true` and surface in the top tier. When the only consumers are `diff`, `cmp`, `sha256sum`, `cat`, file reads from `jq`/`yq`, or `git push`: tag `executes_cloned_code: false` and surface as advisory. Today's report has to do this classification by hand.

### R4 — `.yarnrc` (yarn-classic) `--frozen-lockfile true` not surfaced in the digest

**Where**: `/Users/jan/git/dashboard/.yarnrc` (single line: `--frozen-lockfile true`).

**Why missed**: The Node section inspects `.yarnrc.yml` (yarn-berry) but not the legacy `.yarnrc` (yarn-classic). When the classic config sets `--frozen-lockfile true`, every install fails on lockfile drift — this is a positive signal worth recording.

**Proposed change**: Extend the `.yarnrc.yml` parser to also read `.yarnrc` (key/value, one per line, leading `--` allowed) and surface `frozen_lockfile: bool` plus `registry: <url>` in the same `package_descriptors[].yarnrc` block. Annotate the Node summary row with `frozen-lockfile ✓` when set.
