## Open issues

### Top tier — moving-branch fetches executed in build/test paths

- `cypress/jenkins/init.sh:36` — `git clone -b "${QA_INFRA_BRANCH}" "${QA_INFRA_REPO}" "${QA_INFRA_DIR}"` defaults `QA_INFRA_BRANCH=main` and `QA_INFRA_REPO=rancher/qa-infra-automation`. The clone feeds `docker build -f Dockerfile.quickstart` (line 44) and a subsequent `docker run` of the resulting image (line 222), so anyone with push access to `qa-infra-automation@main` controls the bytes that execute in CI. Pin to a 40-hex SHA, vendor the playbook, or add `git rev-parse HEAD` verification against a stored value.
- `shell/scripts/test-plugins-build.sh:201` — `git clone https://github.com/$REPO_ORG/$REPO_NAME.git` with no `--branch` flag, then `yarn install --frozen-lockfile` and `yarn build-pkg` on the result (lines 205, 220). Five extension repos clone this way (`kubewarden-ui`, `manager-ext`, `harvester-ui-extension`, `ali-ui`, `virtual-clusters-ui`). A push to any of those defaults branches lands in the test runner. Pin each clone to a release tag commit, or vendor the test fixtures.
- `scripts/get-branch-metadata.sh:19` — `curl -s -f -L https://raw.githubusercontent.com/rancher/dashboard/master/branches-metadata.json`. The JSON sets `UI_INDEX` in `scripts/build-e2e:58`, which becomes the URL fetched at `scripts/build-e2e:62` and shipped as the e2e ember UI. Self-fetching from `master` means anyone who lands a PR on master can redirect every future e2e build's UI to an arbitrary URL. Replace with a relative path (`cat ./branches-metadata.json`) — the file already lives in this repo.
- `shell/scripts/extension/helm/package/Dockerfile:1` — `FROM registry.suse.com/bci/bci-base:15.5` with no `@sha256:` digest. The image gets rebuilt on every chart publish; a registry compromise or tag re-push lands directly in the published extension chart. Pin with `FROM registry.suse.com/bci/bci-base:15.5@sha256:<digest>` and let Renovate (or Dependabot once SUSE registry support lands) keep it current.

### GitHub Actions token permissions

GitHub Actions runs every job with a `GITHUB_TOKEN` whose scope is set by the workflow's `permissions:` block. A missing block defaults to broad write access; explicit `write` on `contents`, `packages`, `id-token`, `actions`, `deployments`, or `pages` lets a compromised step push code, mint releases, vend OIDC tokens, or alter past workflow runs.

- 26 workflows lack a top-level `permissions:` block (`.github/workflows/add-issue-labels.yaml`, `automation-candidate.yaml`, `build-and-upload-branch.yaml`, `build-and-upload-release.yaml`, `build-and-upload.yaml`, `build-extension-catalog.yml`, `build-extension-charts.yml`, `build-extensions-test.yml`, `build-test.yaml`, `check-plugins.yaml`, `code-coverage.yaml`, `create-pr-build-extension-charts.yml`, `docusaurus.yaml`, `extensions-compatibility-tests.yaml`, `port-issue.yaml`, `port-pr.yaml`, `pr-gh-project-processor.yaml`, `pr-gh-project.yaml`, `rancher-components.yaml`, `storybook.yaml`, `test-extension-workflows-master.yml`, `test-extension-workflows-release-2.8.yml`, `test-extension-workflows-release-2.9.yml`, `test.yaml`, `update-cloud-data.yml`, `valid-pr.yaml`). Add `permissions: read-all` at the top level.
- 52 sensitive-write declarations across 22 workflows. Highlights:
  - `.github/workflows/agentics-maintenance.yml:127,147,148,201` — `actions: write` and `contents: write`.
  - `.github/workflows/build-extension-charts.yml:120-123` — `actions/contents/deployments/pages: write` (publishes the gh-pages site).
  - `.github/workflows/test-extension-workflows-master.yml:66-83` and the `release-2.8` / `release-2.9` siblings — `actions/contents/deployments/pages/packages: write`.
  - `.github/workflows/auto-retry.yaml:17` — workflow-level `actions: write` (a compromise can rerun arbitrary past workflows with their secrets).
  - `.github/workflows/release-cypress-pkg.yaml:22`, `.github/workflows/release-rancher-components.yml:9`, `.github/workflows/release-shell-pkg.yaml:24`, `.github/workflows/fossa.yaml:14`, `.github/workflows/automation-candidate.yaml:17`, `.github/workflows/port-issue.yaml:15`, `.github/workflows/port-pr.yaml:14`, `.github/workflows/pr-gh-project-processor.yaml:16`, `.github/workflows/docusaurus.yaml:50`, `.github/workflows/update-cloud-data.yml:16` — `id-token: write` (lets the job mint OIDC tokens to cloud providers).
- 60 less-sensitive write declarations on `issues`, `pull-requests`, `discussions`, `repository-projects`. Less dangerous than the sensitive set, but still worth narrowing — most of these workflows only need `read` on the rest of the token surface plus the one scope they use.

Audit each workflow against the principle "the lowest-privilege token that gets the job done." A typical pattern: top-level `permissions: read-all`, then per-job `permissions:` granting only the one or two scopes that job needs.

## Retro: dependency types not explicitly covered

R1. **Inventory verifier-matcher misses variable references and templated basenames.**
- **Where**: `.github/actions/install-chrome/action.yaml:19` (templated filename), `scripts/e2e-k3s-start:53,69` (variable-name verifier).
- **Why missed**: The script's basename matcher only matches when the verifier's basename literal equals the candidate's destination literal. It does not handle the `${VAR}` form (`sha256sum get_helm.sh` against `curl -o get_helm.sh ...` worked, but `DOWNLOADED_CHECKSUM=$(sha256sum get_helm.sh ...) … "$DOWNLOADED_CHECKSUM" != "${HELM_CHECKSUM}"` did not), and it doesn't strip GHA template syntax from filenames.
- **Proposed change**: Extend the matcher to (a) recognize the `*_CHECKSUM`/`*_SUM`/`*_SHA256` shell-variable comparison form even when it sits a few lines after the `sha256sum` invocation, and (b) strip `${{ ... }}` and `${VAR}` segments from candidate basenames before matching.

R2. **Localhost / loopback URLs misclassified as downloads.**
- **Where**: `shell/scripts/test-plugins-build.sh:54` (`curl http://localhost:4873/...`), `.github/workflows/daily-accessibility-review.lock.yml:357` (`curl https://127.0.0.1:8443/v3-public/...`).
- **Why missed**: The candidate filter looks at curl flags (`-o`, `>`, archive extension) but not at the destination host. Localhost and `127.0.0.1` URLs cannot be supply-chain downloads — they target a process the same script just started.
- **Proposed change**: Add a destination-host filter to the inline-download detector. Drop candidates whose host is `localhost`, `127.0.0.1`, `::1`, or `0.0.0.0`. Keep them as zero-priority advisories rather than open issues.

R3. **GitHub API JSON responses misclassified as code downloads.**
- **Where**: `scripts/build-upload-gate:37,40` (`curl https://api.github.com/repos/...`), `.github/workflows/scripts/request.js:302` and `pr-gh-project.js:147,178,291` (`https.get('https://api.github.com/...')` / `request.fetch()`).
- **Why missed**: The detectors flag any `curl https://...` to a tmp file and any `https.get`/`fetch` call. They cannot tell that `api.github.com` returns JSON the script parses with `jq-nano`/`JSON.parse`, not bytes the script executes.
- **Proposed change**: Add an allowlist of API hosts (`api.github.com`, `api.gitlab.com`, `dev.azure.com/_apis/`, `bitbucket.org/!api/`) that, combined with a JSON-parse sink (`jq`, `JSON.parse`, `python -c "import json"`), reclassifies the candidate as an API call rather than a download.

R4. **`npx <local-tool>` flagged as registry fetch even when the tool is in `devDependencies`.**
- **Where**: `cypress/scripts/build.sh:60` — `npx tsc` invokes the locally installed `typescript`.
- **Why missed**: The run-from-network rule treats every `npx`/`bunx` as registry-fetched. It does not check whether the binary resolves locally first.
- **Proposed change**: When `npx <name>` (no `@version` suffix and no URL) resolves against the nearest `package.json`'s `dependencies` / `devDependencies`, treat it as a local invocation. The script already has access to the repo's `package.json` files; cross-reference `npx <name>` candidates against the closest manifest's deps.

R5. **`git clone` without `--branch` flag silently uses the remote's default branch.**
- **Where**: `.github/workflows/scripts/publish-storybook:25`, `.github/workflows/scripts/retrieve-versions.sh:31`, `shell/scripts/test-plugins-build.sh:201`.
- **Why missed**: The `git_clones_in_scripts[]` detector records `branch_or_tag: None` for these. The classification ("non-SHA ref") is correct, but the digest could lift them out of the catch-all bucket and surface "default-branch clone (likely `main`/`master`)" so the report can prioritize the executed-vs-read-only distinction more cleanly.
- **Proposed change**: For `git clone` candidates with no `--branch`, add a `default_branch_assumed: true` field. Pair with a follow-up scan of the same script body for `yarn install`, `npm install`, `docker build`, `helm install`, etc. on the clone's destination directory and emit `executes_clone: true|false`. The report's top-tier vs. lower-severity split then becomes mechanical.

R6. **Helm / OCI / mirrored binary fetches that land in published artifacts.**
- **Where**: `shell/scripts/extension/publish:400` — `wget index.yaml` from the user's own gh-pages branch and merges it into `helm repo index --merge`.
- **Why missed**: The inline-download rule flags it correctly, but the threat model — mutated metadata flowing into a published Helm index — deserves its own bucket because the fix is different (the file should round-trip through git, not over HTTPS).
- **Proposed change**: Add a "published-artifact ingestion" check: any `*.yaml`/`*.json`/`index.yaml` fetched into a script that subsequently runs `helm repo index --merge`, `oras push`, `docker push`, `npm publish`, `gh release upload`, etc. surfaces as a top-tier finding regardless of the script's other pinning posture.
