GitHub Actions token permissions — missing top-level block (default = read/write) ¶

  • 26 workflows lack a top-level permissions: declaration, so each job runs with the repo-default token (commonly read/write on legacy repos). With actions/, id-token, and packages write available by default, a compromised pinned action can publish artifacts, mint OIDC tokens, or push code. Add permissions: read-all at the workflow level and grant the narrowest write per-job that needs it.
  • Workflows: add-issue-labels.yaml, automation-candidate.yaml, build-and-upload-branch.yaml, build-and-upload-release.yaml, build-and-upload.yaml, build-extension-catalog.yml, build-extension-charts.yml, build-extensions-test.yml, build-test.yaml, check-plugins.yaml, code-coverage.yaml, create-pr-build-extension-charts.yml, docusaurus.yaml, extensions-compatibility-tests.yaml, port-issue.yaml, port-pr.yaml, pr-gh-project-processor.yaml, pr-gh-project.yaml, rancher-components.yaml, storybook.yaml, test-extension-workflows-master.yml, test-extension-workflows-release-2.8.yml, test-extension-workflows-release-2.9.yml, test.yaml, update-cloud-data.yml, valid-pr.yaml.

Retro: dependency types not explicitly covered ¶

R1 — `kubectl apply -f <pinned-version-URL>` falsely classified as verified ¶

Where: scripts/e2e-k3s-start:81.

Why missed: inventory.py's run_from_network[] detector recognises kubectl apply -f URL and runs the ±30-line verifier scan. The window picked up K3S_CHECKSUM / HELM_CHECKSUM blocks for the two unrelated downloads on lines 53–58 and 69–75 and stamped this entry verifier ✓. The verifier targets k3s-script and get_helm.sh, not cert-manager.crds.yaml.

Proposed change: For run_from_network[] kubectl apply -f URL entries, require the verifier line to name the URL's filename basename (cert-manager.crds.yaml) or to live in the ±10 line window. The same destination-name match already exists for curl/wget candidates per the Phase 2 rules — extend it to kubectl apply -f and to helm install from a remote chart.

R2 — `gh-aw` agentic-workflow lock.yml manifests as a first-class pinning signal ¶

Where: .github/workflows/*.lock.yml (7 files, e.g. daily-accessibility-review.lock.yml).

Why missed: The script's existing GHA + container-image scanners parse the compiled body and report what they find, which means each lock.yml looks like an unpinned-permissions soup of sensitive-writes. But the file's gh-aw-manifest header (line 2) embeds a structured manifest that pre-pins every actions[].sha and containers[].digest and lists every secret the workflow can touch. Treating the manifest as authoritative would:

  • Confirm the body's pinning posture without re-parsing every uses: and image: line in a 1500-line generated file.
  • Distinguish "compiled from .md spec, audit the manifest" from "hand-written workflow, audit each line."

Proposed change: Add a gh_aw_lock_files[] section to the inventory. For each .lock.yml whose first comment line matches # gh-aw-metadata:, parse the second comment line (# gh-aw-manifest:) as JSON and emit compiler_version, actions[], containers[], secrets[]. In Phase 2 and Phase 3, suppress the per-line uses: / image: and permissions: findings for these files when actions[].sha matches every uses: SHA in the body — surface a single Pinned dependencies › gh-aw lock files row instead. Hand-written privileged scopes still warrant per-finding bullets so they're visible in the report.

R3 — `git clone` followed by `docker build` / `yarn build-pkg` should rate higher than `git clone` followed by `diff` ¶

Where: cypress/jenkins/init.sh:36-46, shell/scripts/test-plugins-build.sh:201-220, .github/workflows/scripts/check-creators-workflows-code.sh:89 (compare).

Why missed: The script's git_clones_in_scripts[] flags every non-SHA clone uniformly. There's no notion of "what does the script do with the clone." A clone that feeds docker build or yarn build-pkg is in the same threat tier as curl | bash; a clone that feeds diff is advisory.

Proposed change: After detecting a git clone, scan the next ~50 lines (or the rest of the function body) for docker build, yarn build, yarn install, npm install, make, cargo build, go build, ansible-playbook, python setup.py install, pip install -e .. When any match: tag the entry executes_cloned_code: true and surface in the top tier. When the only consumers are diff, cmp, sha256sum, cat, file reads from jq/yq, or git push: tag executes_cloned_code: false and surface as advisory. Today's report has to do this classification by hand.

R4 — `.yarnrc` (yarn-classic) `--frozen-lockfile true` not surfaced in the digest ¶

Where: /Users/jan/git/dashboard/.yarnrc (single line: --frozen-lockfile true).

Why missed: The Node section inspects .yarnrc.yml (yarn-berry) but not the legacy .yarnrc (yarn-classic). When the classic config sets --frozen-lockfile true, every install fails on lockfile drift — this is a positive signal worth recording.

Proposed change: Extend the .yarnrc.yml parser to also read .yarnrc (key/value, one per line, leading -- allowed) and surface frozen_lockfile: bool plus registry: <url> in the same package_descriptors[].yarnrc block. Annotate the Node summary row with frozen-lockfile ✓ when set.
